# Load tests (k6)

The scripts in `scripts/k6` send real HTTP traffic to a running server. They answer two kinds of questions:

- **Is the data still correct when many requests arrive at once?** (`ledger.js`)
- **How fast is the server, and when does it break?** (`dashboard.js`, `stress.js`)

| Script | What it tests | Users it logs in as | Runtime |
|---|---|---|---|
| `ledger.js` | Balances, limits and deadlocks under parallel writes | 1 | about 1 minute |
| `dashboard.js` | Normal load: people opening the dashboard | up to 50 | about 5 minutes |
| `stress.js` | Rising load until the server slows down or fails | as many as it needs, up to `SEED_USERS` | about 7.5 minutes |

## Before you run

Install [k6](https://grafana.com/docs/k6/latest/set-up/install-k6/). Then start a server for the scripts. There are two ways.

### Option 1: one command (recommended)

```sh
make loadtest test=ledger      # or dashboard, stress
```

This needs Docker. It does not touch your dev database. It:

1. starts a new Postgres container (`wealth-warden-loadtest-postgres`, database `wealth_warden_loadtest`) and a new Redis container
2. runs the migrations
3. seeds lean bulk users: users, settings, categories, and 3 cash accounts with transactions. No saving goals, no investments.
4. starts the app, with River and its periodic jobs, on `http://localhost:2100`
5. runs the k6 script with the right settings
6. for `ledger` only: runs the ledger check and prints the table
7. stops the app and removes the containers

The command fails if a k6 threshold fails, or if a row of the ledger check is not `t`. Press Ctrl+C to stop early; the containers are still removed.

The app's logs go to `logs/loadtest.log`, so the terminal shows only the k6 output. Per-request log lines are turned off.

Your own script settings pass through to k6:

```sh
RACERS=10 make loadtest test=ledger
```

To run k6 by hand, for example several times on one server, add `serve=1`. The command then only starts the server and prints the k6 command to run. Press Ctrl+C to stop it.

```sh
make loadtest test=ledger serve=1
```

The seed uses a fixed random seed and fixed settings, so every start gives the same data. The number of users depends on the test:

| Test | Users | Why |
|---|---|---|
| `ledger` | 1 | It logs in as one user |
| `dashboard` | 50 | Up to 50 virtual users |
| `stress` | 1000 | Up to `SEED_USERS` virtual users |

To change them, add `users=` or `port=`:

```sh
make loadtest test=dashboard users=1000 port=2200
```

With only 50 users, the database is small and stays in memory. Use `users=1000` to test the dashboard on a bigger database.

Lean users have 3 accounts instead of 5, and no investment snapshots. Results from this server do not compare with results from a full bulk seed.

### Option 2: your dev server

Start the server. The scripts expect it on `http://localhost:2000`. Seed the bulk test users:

```sh
go run ./cmd seed bulk --users 1000           # add --lean to skip saving goals and investments
```

This creates `bulk00001@seed.local` to `bulk01000@seed.local`, all with the password `password`. The domain comes from `seed.bulk.email_domain` in the config file. If your config uses another domain, pass it to the scripts with `EMAIL_DOMAIN`.

All scripts accept `BASE_URL` if the server runs somewhere else.

## ledger.js: correctness under parallel writes

This test tries to break the money rules. It logs in as one user and creates 5 new accounts for the run. Then it runs three things:

- **Expense race:** 50 expenses of 100 at the same moment, on an account that holds 1000. At most 10 may succeed.
- **Transfer race:** 50 transfers of 100 at the same moment, from an account that holds 1000. At most 10 may succeed.
- **Churn:** for one minute, 20 users insert, edit and delete transactions, and transfer money in both directions between two accounts. This is where deadlocks show up.

`make loadtest test=ledger` runs the test and the check for you. To run it by hand:

```sh
k6 run scripts/k6/ledger.js
```

At the end, k6 prints a check command for the run. Run it without the trailing `source=console`:

```sh
docker exec -i <container> psql -U <user> -d <database> -v run="k6 ledger <run id>%" < scripts/k6/ledger_check.sql
```

The container, user and database come from `PG_CONTAINER`, `PG_USER` and `PG_DB`. The k6 command from `make loadtest serve=1` sets them. Without them, the command uses the dev database.

**The test passes when:**

- `accepted_expenses` and `accepted_transfers` are 10 or less
- `server_errors` is 0
- every row of the check is `t` in all three columns:
  - `matches_ledger`: the stored balance equals the sum of the account's transactions
  - `within_limit`: the balance is not below the account's limit
  - `matches_snapshot`: the latest daily snapshot equals the stored balance

About 3% of requests show as failed. That is normal: k6 counts every 4xx as a failure. These are the rejected expenses and transfers, and edits of transactions that another user deleted first.

**Each run adds 5 accounts to the user.** A user can have at most 25 active accounts (the `max_accounts_per_user` setting). Bulk users start with 5 accounts, or 3 if lean. After 4 runs, the setup fails with "you can only have 25 active accounts". `make loadtest` starts with a fresh database every time, so this only matters with `serve=1` or the dev server. On the dev server, switch to another user, or reseed:

```sh
LEDGER_EMAIL=bulk00002@seed.local k6 run scripts/k6/ledger.js
```

## dashboard.js: normal load

Each virtual user logs in once, then opens the dashboard again and again, with 1 to 3 seconds of pause between loads. One dashboard load is 13 requests, sent in the same order and grouping as the web client.

The number of users rises from 10 to 50 and then goes back to 0.

```sh
k6 run scripts/k6/dashboard.js
```

**The test passes when** less than 1% of requests fail, 95% of requests finish in under 500 ms (overall and for each endpoint), and more than 99% of checks pass.

## stress.js: find the breaking point

This test does not use a fixed number of users. It sets a fixed number of dashboard loads per second and raises it in steps: 25, 50, 100, 200 and 400 per second. If the server gets slower, k6 adds more virtual users to keep up the rate. Each new virtual user logs in as the next bulk user.

```sh
k6 run scripts/k6/stress.js
```

The test stops early if more than 5% of requests fail, or if 95% of requests take longer than 1 second. That is the expected end of a stress run, not a bug in the script. Look at:

- which step was running when it stopped
- the per-endpoint times, to see which request slowed down first
- `dropped_iterations`: loads k6 could not start, because it had no free virtual user

## Settings

| Variable | Used by | Default | Meaning |
|---|---|---|---|
| `BASE_URL` | all | `http://localhost:2000` | Server address |
| `PASSWORD` | all | `password` | Password of the bulk users |
| `LEDGER_EMAIL` | ledger | `bulk00001@seed.local` | The one user the ledger test logs in as |
| `RACERS` | ledger | `50` | Parallel expenses and transfers in the races |
| `SEED_USERS` | dashboard, stress | `1000` | How many bulk users exist |
| `EMAIL_DOMAIN` | dashboard, stress | `seed.local` | Domain of the bulk users |
| `PG_CONTAINER` | ledger | `postgres-postgres-1` | Postgres container in the printed check command |
| `PG_DB` | ledger | `wealth_warden` | Database in the printed check command |
| `PG_USER` | ledger | `postgres` | Database user in the printed check command |

## Users and scale

The scripts do not look up how many users exist. They use:

- **ledger.js:** one user.
- **dashboard.js:** one user per virtual user, so users 1 to 50.
- **stress.js:** one user per virtual user. It adds virtual users only when it needs them, up to `SEED_USERS`. A fast server needs a few hundred; a slow one needs more.

Never set `SEED_USERS` higher than the number of users you seeded. A virtual user with no matching bulk user cannot log in, and the run fails.

Seeding more users makes the database bigger, but the tests still log in as the same small number of users. 1000 bulk users take about 1 GB; 10,000 take about 10 GB. Requests read only their own user's rows through indexes, so a bigger database mostly costs cache hits: Postgres has to read more from disk once the active users' data no longer fits in memory. Background jobs that loop over all users, such as the price sync, also take longer and can overlap with a test run.
